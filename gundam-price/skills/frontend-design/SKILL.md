# 前端设计自检清单（frontend-design）

## 这个 Skill 是干什么的

把「高达行情」项目里已经确认过的前端规则固化成一张**可逐条勾选的检查表**。

以前这些规则靠我临时想起来，每次可能不一样；现在写死在文件里，**每次改动都用同一把尺子量**，量完还要留记录。

**怎么用（两步，别跳）：**

1. **写完前端代码后**，从头到尾对照下面「二、检查项」逐条过一遍。
2. 通过的在「四、使用记录」里记一行：日期 + 检查对象 + 有没有发现问题 + 结论。**没记录 = 没检查过。**

**适用范围：** `gundam-price/` 下所有 HTML / CSS / JS 的前端部分。

## 二、检查项（逐条勾选）

### A. 对比度与可读性

- [ ] **A1** 正文与背景对比度 ≥ **4.5:1**；大号文字（≥18px 或 ≥14px 加粗）≥ **3:1**。
- [ ] **A2** 灰色辅助文字不能因为「想显得淡」就调太浅——项目里统一用变量 `--ink-muted`（`#6b7280`），不要另写 `#999` 一类的浅灰。
- [ ] **A3** 颜色不是唯一的信息载体：档位（捡漏/合理/溢价）除了颜色，还有文字标签。
- [ ] **A4** 字号 ≥ 12px（项目页脚最小 12px），行高 ≥ 1.5。

### B. 交互反馈（用户每次操作都感知得到，优先级最高）

- [ ] **B1** 所有可点击元素有 **hover** 视觉变化（下划线 / 位移 / 阴影 / 变色）。
- [ ] **B2** 所有可点击元素有 **键盘焦点** 反馈：用 `:focus-visible` 给外框（`outline: 2px solid var(--accent)`），**不要**用 `outline: none` 直接抹掉。
- [ ] **B3** 异步操作有中间态（如收藏的「保存中…」+ 按钮禁用防连点）。
- [ ] **B4** 操作结果有明确反馈：成功/失败都要有提示，失败要能看出「失败了」，不能静默。
- [ ] **B5** 有状态切换的控件（如收藏按钮）用 `aria-pressed` 表达当前状态。

### C. 信息层级与布局

- [ ] **C1** 一屏内最想让人看到的信息（价格、结论）在视觉上要最重：字号更大、字重更粗。
- [ ] **C2** 不同信息块之间要有间距区分，不能糊成一片（区块间距 ≥ 10px）。
- [ ] **C3** 长表格/长内容要能横向容纳不撑破：外层加 `.table-wrap`（`overflow-x: auto`）。
- [ ] **C4** 手机端（≤600px）不错乱：卡片单列、内边距收窄、字号不溢出。

### D. 可访问性（余力加练，Day 12 单独立章）

- [ ] **D1** **键盘走通全流程**：Tab 能依次到达每个可交互元素，Enter/Space 能激活，顺序与视觉顺序一致。
- [ ] **D2** **焦点不被吞**：不用 `tabIndex = -1` 把可聚焦元素踢出键盘序列（除非它只是装饰）。
- [ ] **D3** **事件冒泡要挡住**：控件嵌在可点击容器里时（如收藏按钮嵌在卡片里），控件自己的点击/回车必须 `stopPropagation`，否则会**连带触发外层动作**（Day 11 就踩过：点收藏会跳详情页）。
- [ ] **D4** **语义标签**：按钮用 `<button type="button">`、输入框配 `<label>`、图片写 `alt`。
- [ ] **D5** **图标/符号不裸奔**：`☆` 这类符号要配文字（如「收藏」），或加 `aria-label`，让读屏能听懂。
- [ ] **D6** **状态变化要播报**：如「没有找到相关内容」这类结果提示，用 `role="status"` 或 `aria-live="polite"`，让读屏用户也知道变了。
- [ ] **D7** **图片兜底**：图片加载失败要有文字占位（项目里用 `onerror` 换占位块），不出现裂图。

### E. 动效克制

- [ ] **E1** 动画时长 ≤ 300ms（项目里卡片翻转 300ms、气泡 250ms、抖动 350ms）。
- [ ] **E2** 动效服务于语义（提示状态变化 / 引导视线），不为炫技而加。
- [ ] **E3** 动画不用 `!important` 强推，也不阻断操作（加载动画不能锁住用户）。
- [ ] **E4** 尊重系统「减少动态效果」偏好：`@media (prefers-reduced-motion: reduce)` 下关掉位移/缩放类动画。

## 三、检查完怎么处理

- **全部通过** → 记一行使用记录，交付。
- **有不通过** → **先修，再交付**；修不动的（比如需要素材、需要你拍板）→ 单独列出来告诉我，不要含糊过去。
- **规则本身要改** → 改这个文件，并在「使用记录」里说明为什么改。

### 2026-09-28 ｜ Day 12 筛选交互（首次真实调用）

**一句话结论：这个 Skill 检查的是「改动过的前端代码在对比度、交互反馈、信息层级、可访问性、动效五个方面有没有踩坑」——本次查出 3 处不合格（B2 焦点反馈、D6 结果播报、E4 减少动效偏好），已全部修复。**

**回归测试：** 用 Node 桩 DOM 干跑 19 项断言（初始化 / 有结果 / 有结果+平台叠加 / 收窄 / 无结果 / 清空恢复 / 大小写与空格边界 / 事件绑定）——**19 通过 0 失败**，临时脚本跑完已删除。

**发现的共性问题（已反哺本文件）：** 初版只顾「功能跑通」，最容易漏的是**键盘焦点反馈（B2）、读屏播报（D6）、减少动态效果（E4）**——这三条不影响肉眼看着「没问题」，但正是可访问性的核心。下次写新控件，这三条优先过一遍。
