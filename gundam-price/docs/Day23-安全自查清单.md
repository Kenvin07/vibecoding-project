## 二、逐项明细

### 1. 代码里没有硬编码密钥

**结论**：通过。全仓库扫描密钥真值 **0 条**。

**为什么不能直接搜 `password` / `secret` / `apikey`**
直接搜这些词会命中两种完全不同的东西：一类是**变量名与文档说明**（`process.env.WRITE_API_KEY`、注释里「密钥只放环境变量」），这是**正确做法**；另一类是**真正的密钥真值**（`WRITE_API_KEY = "a3f9c1..."`），这才是要抓的。前者命中等于报警器对着自家门牌狂响。

所以本项的搜索词瞄准「**真值的长相**」：键名 + 等号/冒号 + 引号里的 6 位以上字符串，再加上 `sk-` / `AKID` / PEM 私钥头 / 带密码的连接串。

**验证方法**

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"
sh gundam-price/scripts/check-secrets.sh
```

**预期结果**

```
【命中结果】
  （无输出）

【命中条数】0
【结论】未发现密钥真值 —— 通过
```

**附加：证明这个脚本不是「永远返回 0」的摆设**（灵敏度自测）

```bash
mkdir -p /tmp/t && printf 'WRITE_API_KEY = "deadbeefdeadbeef";\n' > /tmp/t/f.js
sh gundam-price/scripts/check-secrets.sh /tmp/t
```

**预期结果**：`【命中条数】1`。能抓到假的，才说明「0 条」是真结论。

### 2. `.env` 不在仓库、且被忽略

**结论**：通过。工作区不存在 `.env`，且它从未被 Git 跟踪。

**验证方法**

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"

# ① 已跟踪的文件里有没有「真」密钥类文件（预期：无输出）
#    末尾的 grep -v 是为了排除 .env.example —— 它是模板，是【应该】进仓库的，
#    不排除的话会看到它，容易误判成「有敏感文件被提交」。
git ls-files | grep -iE "\.env|\.pem|\.key|credential|secret" | grep -v "\.env\.example"

# ② .env 是否被忽略（预期：显示它命中了哪一条忽略规则）
git check-ignore -v .env
```

**预期结果**

- ① 无输出
- ② 显示 `.gitignore:20:.env　.env` —— 说明 `.env` 确实被规则挡住

> 行号（20）会随 `.gitignore` 后续增删而变，看的是「有没有命中」而不是「第几行」。

### 3. `.gitignore` 覆盖完整

**结论**：通过。补齐了 `.env` 变体、私钥文件、系统杂物三类缺口。

**改前的缺口**（实测确认）：`.env.local`、`.env.production`、`*.pem`、`*.key` 均**未**被忽略。

**验证方法**（一条命令批量验证，预期全部显示「已忽略 ✓」）

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"
for p in ".env" ".env.local" ".env.production" "gundam-price/.env.local" \
         "server.pem" "gundam-price/cert.pem" "server.key" ".DS_Store" "Thumbs.db"; do
  printf "  %-32s " "$p"; git check-ignore -q "$p" && echo "已忽略 ✓" || echo "未忽略 ✗"
done
```

**要点**：`.gitignore` 里 `.env` 和 `.env.*` **两行都必须有**。
原因：`.env.*` 里的 `*` 表示「点后面还得有内容」，所以光秃秃的 `.env` 匹配不上它。

### 4. `.env.example` 可提交且无真值

**结论**：通过。模板已进仓库，且里面一个真值都没有。

**为什么模板能进仓库、`.env` 不行**
`.env.example` 是**菜谱**（写着「该放什么」），`.env` 是**做好的那盘菜**（装着真东西）。菜谱可以传阅，菜不行。所以规则是「忽略所有 `.env*`，但用 `!` 单独放行 `.env.example`」。

**验证方法**

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"

# ① 能不能真的被 add（预期：显示 add 'gundam-price/.env.example'）
git add --dry-run gundam-price/.env.example

# ② 里面的变量行，等号后面是不是空的（预期：四行等号后为空或默认值）
grep -nE "^[A-Z_]+=" gundam-price/.env.example

# ③ 用密钥脚本扫它本身（预期：0 条）
sh gundam-price/scripts/check-secrets.sh gundam-price/.env.example
```

**预期结果**：`CLOUDBASE_ENV_ID=`、`CLOUDBASE_API_KEY=`、`WRITE_API_KEY=` 三行等号后为空；`PORT=9000` 是默认值（非敏感）。

> **顺序提醒**：`.gitignore` 里 `!.env.example` 必须写在 `.env.*` **之后**。Git 是「后面的规则覆盖前面的」，顺序反了就失效。

### 5. Git 历史中从未提交过密钥

**结论**：通过。历史干净，**无需作废密钥**。

**为什么必须查历史**
代码里删掉密钥 ≠ 安全。Git 会保存每一次提交的内容，旧提交里的密钥仍然能被翻出来。所以「删代码」和「作废密钥」是两件事 —— 一旦历史上出现过真密钥，唯一正确的做法是**去平台把密钥作废、重新生成**，光清理代码没用。

**验证方法**

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"

# ① 历史里有没有「键名 = 引号长串」这种赋值（预期：无输出）
git log --all -p | grep -nE "^\+.*(password|passwd|secret|api[_]?key|apikey|token|access[_]?key|private[_]?key)[A-Za-z0-9_]*[[:space:]]*[:=][[:space:]]*[\"'][^\"']{6,}"

# ② 历史里有没有 .env 被新增过（预期：无输出）
git log --all --diff-filter=A --name-only --pretty=format: | sort -u | grep -iE "\.env|\.pem|\.key|credential"
```

**预期结果**：两条命令均无输出。

**本次实查结论**：历史上所有 `WRITE_API_KEY` / `CLOUDBASE_API_KEY` 相关行都是**变量名引用或文档说明**，无一处赋值真值；`.env` 从未被提交。

### 6. 三类错误都返回中文提示

**结论**：通过。前端统一为三类中文提示，后端本就是全中文。

**三类错误的定义**

| 类别 | 触发场景 | 用户看到的文案 |
|---|---|---|
| ① 输入错 | 400 / 401 / 404 / 409（后端校验拦住） | **后端给的中文原文**，如「price 必须是不小于 0 的整数（暂无报价就不传）」 |
| ② 网络错 | 断网 / 域名解析失败 / 跨域被拦 | 「连不上服务器，请检查网络后重试」 |
| ③ 服务端错 | 5xx / 返回坏 JSON / 状态码缺失 | 「服务器暂时无法处理请求，请稍后重试」 |

**验证方法**：浏览器打开首页，在网址后加参数（注意用 `?` 开头）

| 类别 | 地址栏写法 | 预期看到 |
|---|---|---|
| 网络错 | `…/index.html?err=network` | 连不上服务器，请检查网络后重试 |
| 服务端错 | `…/index.html?err=server` | 服务器暂时无法处理请求，请稍后重试 |
| 输入错 | `…/index.html?err=input` | price 必须是不小于 0 的整数（暂无报价就不传） |

> `?err=` 是**临时演示开关**：只在页面加载时伪造一个本地错误，**不发任何请求、不碰数据**。把参数删掉刷新即恢复。

**后端本来就达标**：`cloudfunctions/` 里的错误文案全部是中文，且已按 400/401/404/409/500 分类（Day 18–22 的成果）。本次**未改动后端一行代码**。

### 8. 技术细节不丢失（可排查）

**结论**：通过。细节不是被删掉，而是被**移到 F12 控制台**。

**为什么这么设计**
用户看不懂技术细节 ≠ 技术细节没用。正确做法是**分层**：给用户的话说人话，给开发者的细节留日志。所以报错时页面显示中文人话，同时控制台打印一条带原始英文、状态码、错误码的日志。

**验证方法**

1. 打开任一错误页面（如 `…/index.html?err=server`）
2. 按 `F12` → 切到 `Console`（控制台）标签
3. 应看到一行以 `[错误]` 开头的日志

**预期结果**：日志形如

```
[错误] 服务器暂时无法处理请求，请稍后重试　←　HTTP 500 | code=INTERNAL_ERROR | 原始信息: Internal Server Error
```

前半段是给用户的人话，后半段是给排查者的原始信息。

### 9. 非法输入被拦截

**结论**：通过。后端有统一校验层，非法输入返回 400 + 中文说明。

**验证方法**

```bash
cd "/c/Users/13546/Desktop/vibecoding打卡project"
grep -n "throw new HttpError(400" gundam-price/cloudfunctions/api/services/*.js gundam-price/cloudfunctions/api/lib/*.js
```

**预期结果**：能看到大量 400 校验分支，覆盖：正整数范围、日期格式与真实性、枚举取值、必填字段、请求体大小、JSON 合法性等。

**举例**（实测返回的中文提示）：

- `limit 必须是正整数`
- `updatedDate 必须是 YYYY-MM-DD 的真实日期，例如 2026-10-06`
- `platform 只能是 拼多多 / 淘宝 / 京东 / 闲鱼 / 其他`
- `请求体过大`
- `note 最长 100 个字符`

**为什么「真实日期」要单独校验**：`2026-02-30` 格式完全正确，但 2 月没有 30 号。校验方式是把日期交给 `Date` 解析后再转回字符串比对，对不上就是假日期。

**同类约定**（项目一直遵守）：密钥只放云函数环境变量；不进代码、不进 Git、不截图、不粘进聊天记录。
