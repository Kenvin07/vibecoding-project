## ① 用户问题（约 40 秒）

**要讲清三件事：**

1. **谁的问题**：想买 MG 高达的玩家，同一台机体在拼多多 / 淘宝 / 闲鱼三个平台价格不一样，还分「行货 / 水货」，翻来翻去难比较。
2. **我要做成什么**：一个能一眼看清「这台机现在最低多少钱、在哪个平台」的比价页；本期收录 **5 台 MG**。
3. **第 3 周要解决的那一层**：前面两周页面已经能看，但**数据是死的**（写在本机的 `data/data.json` 里）。这周把它搬到云上 —— 换台电脑、用手机都能打开，数据存在云数据库里，不是存在我电脑里。

> 可展示：公网首页 https://gundam-market-d7gnjqg3h1f2f156f-1499380808.tcloudbaseapp.com/ （5 张卡片，展示「近 30 天最低」）

## ② 核心流程（约 110 秒）★ 含一次真实写入 + 刷新持久化

**按这个顺序演，一步都别跳：**

| 步 | 动作 | 观众该看到什么 |
|---|---|---|
| 1 | 打开**公网首页**，停在列表 | 5 台机体卡片；其中「MG ν高达 Ver.Ka」显示 **暂无报价**（记下这个状态，等下要变） |
| 2 | 打开**公网检查台** https://gundam-market-d7gnjqg3h1f2f156f-1499380808.tcloudbaseapp.com/check.html | ① 后端健康状态 = 绿色；② 核心表真实数据 = 读出 5 台机体、13 条价格记录 |
| 3 | **本机**打开检查台（`http://localhost:8000/check.html`）；③ 写入测试里先粘贴密钥，点【**只验密钥（不写数据）**】确认绿字（先验钥匙再写，免得白填表），再填表提交 | ③ 段只在本机出现（公网域名下没有这一段 —— 密钥不上前端）；验钥匙应显示「密钥有效 —— 写接口认这把钥匙，数据库零变化」；提交后提示 `写入成功（HTTP 201）` 并给出新编号（本次实测为 `pr_0014`） |
| 4 | 回到**公网首页**，`Ctrl + Shift + R` 强制刷新 | 「MG ν高达 Ver.Ka」从 **暂无报价** 变成一个具体价格 |
| 5 | 回到**公网检查台**，再刷新一次 | ② 核心表真实数据的条数 +1，能看到刚写进去的那条记录 |

**第 4–5 步就是「刷新持久化」的证据**：写入不是只改了我本地页面，而是**真的进了云数据库**，所以公网页面刷新后还在。

**写入用的推荐参数（照抄，避开 409 陷阱）：**

| 字段 | 值 | 说明 |
|---|---|---|
| kitId | `mg-nu-verka` | 这台目前**没有任何报价**，写完效果最明显（暂无报价 → 有价） |
| platform | `pdd` | 只能是 `pdd` / `taobao` / `xianyu` |
| marketType | 保持默认（`水货`） | 只能是 `行货` / `水货`；下拉默认就是水货，不必改 |
| price | 自己填一个整数（如 `420`） | 不小于 0 的整数；不填就是「暂无报价」 |
| updatedDate | `2026-10-10` | `YYYY-MM-DD`，必须是真实日期 |

> ⚠️ **别踩的坑**：防重复的判定是「机体 + 渠道 + 类型 + **日期**」四个一起。
> 如果对着已有组合再写一次（例如 `mg-sazabi-verka` + `pdd` + `行货` + `2026-10-06`），接口会回 **409「该渠道今日已有记录，请使用 PUT 修改」**。演示推荐用 `mg-nu-verka`，它一条记录都没有，绝对不会撞。

## ③ 提示词改写过程（约 50 秒）

讲一条真实的**迭代链**，不要讲「AI 一次就做对了」—— 那既不真实，也没信息量。下面三个例子都出自本周 `api-contract.md` 的变更记录，可当场翻开对照：

| # | 原来的要求 | 撞了什么墙 | 改写后的要求 | 结果 |
|---|---|---|---|---|
| 1 | 「后端直连 PostgreSQL 取数」（写进了技术设计） | 控制台根本不展示数据库「连接信息」（官方文档先于功能上线，社区 issue #1297） | 「改用 **CloudBase 数据网关 REST API + API Key**，不要第三方依赖」 | 当天二改方案，本地桩自检 51/51 通过，Day 17 顺利上线 |
| 2 | PRD：「本期收录 3 台机体」 | 建表后验收要求 `kits` 表「≥ 5 行」，3 行不达标 | 「补 2 台，但**只填真实官方日元价**，没图没销量的字段留空、不许编」 | 5 台落地，`seed.sql` 里如实写 NULL，顺带验证了「暂无报价」的兜底展示 |
| 3 | 契约初版：「接口直接返回数据对象」 | 写代码时发现成功/失败两种形状对不齐，前端不好判断 | 「统一外壳 `{ ok, data, error }`，出错时 `data` 一律为 null」 | 前端解一层壳就够，契约第 1 节按实现重写 |

**可以补一句工作方式上的改写**：不在一条提示词里塞一整天的活，而是**一次只让它做一步、做完先验收**（这条写在自己的 `AGENTS.md` 里）。好处是每一步都有可核对的结果，错了只退一小步。

> 如果现场允许，把当时自己写给 AI 的**原话**贴一句出来（哪怕很口语），说服力比转述强得多。

## ④ 验证方式（约 40 秒）

**核心口径：不说「已完成」，只说「用什么方法、看到什么结果」。** 本周四类证据：

| 验证方式 | 具体做法 | 本周实例 |
|---|---|---|
| 当场实测 | 命令行 `curl` 打公网接口，看状态码与响应体 | `GET /api/health` → 200；无密钥 `POST /api/prices` → **401**（证明确实加了锁） |
| 真库对账 | 改数据库里的数，再读接口，看两边是否同步 | Day 17 把 `pr_0002` 由 230 改成 199，`/api/kits` 的 `minPrice` 同步变 199，改回后复核通过 |
| 文件 + 行号 | 代码/文档证据精确到第几行 | 「SQL 契约」「建表脚本」均给出 `文件:行号`，可逐条打开核对 |
| 独立交叉验证 | **换一个人、换一台机器**验同一件事 | 同伴按 `第3周-交叉验证模板.md` 独立填写三行结论 |

> 本周验收表里唯一 FAIL 的那一项（E2：契约状态标记与变更记录未同步），就是**方法用对了**才暴露出来的 —— 不是没做完，是文档没跟上代码。

|---|---|---|---|
| 1 | 本机服务器开着 | 命令行还在跑 `python -m http.server 8000`，且 `http://localhost:8000/check.html` 能打开、③ 写入测试段可见 | 重新在 `gundam-price` 目录起一次服务器；**写入密钥只在本机模式能用**，别从公网域名打开 |
| 2 | 三个公网地址能打开 | 首页、检查台、接口基址各开一次；检查台 ① 显示绿色、② 有数据 | 多刷一次 `Ctrl + Shift + R`；检查台 ① 若是红的 = 后端没起来，别往下演 |

> 兜底话术：万一写入演示失败，当场说「这次写入失败，我们看接口返回的错码 —— 这恰恰说明挂锁/校验生效了」，再走 ④ 验证方式。**失败也说清楚，比假装成功更可信。**
