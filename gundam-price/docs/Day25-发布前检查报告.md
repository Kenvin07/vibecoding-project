## 一、今天回答的那个问题：故意弄坏了哪一项？

**弄坏的项：S4「前端版本号一致性」。**

**怎么弄坏的**：把 `check.html` 里引用的 `js/api.js?v=20261008` 改成 `?v=20261001`，只改这一个文件、一个数字。

**为什么挑它**：

| 判据 | 说明 |
|---|---|
| 页面照样能打开 | 不白屏、不报错，肉眼完全正常 |
| 功能照样能用 | 版本参数只影响缓存，不影响加载 |
| 只有检查器能发现 | 四个页面对同一个文件的版本号不一致 —— 这正是"看着没问题、上线后有人拿到旧缓存"的典型事故 |

**检查器查出来的原话**（第 1 轮日志）：

```
[FAIL] S4   前端版本号不一致

       期望: 同一文件全站同一个 ?v=；每个本地 js/css 都带 ?v=YYYYMMDD，否则缓存失效不了
```

## 三、误报与漏报反馈（这是今天最值钱的部分）

### 3.1 误报：S1 把文档示例当真密钥（已修）

- **现象**：第 1 轮 S1 报 2 条命中，都指向 `docs/Day23-安全自查清单.md`。
- **真因**：那两行是 Day 23 为了让读者看懂"真值长什么样"、以及"怎么证明扫描脚本不是永远返回 0"而故意写的**假值示例**。
- **判断**：属于误报 —— 但**不能靠改文档来消音**（改掉示例，Day 23 的灵敏度自测就失效了）。
- **修法**：新增 `skills/verify-project/allowlist.txt`，只登记这两条示例，并且检查结果里**如实显示"原始命中 2 / 豁免 2 / 有效 0"**，不悄悄变成 0。
- **二次踩坑**：白名单文件最初把示例写成完整赋值形态，结果**扫描器扫到白名单自己**，又报一条假警。改为只写"值的片段"才解决 —— 凡是扫描工具，都要先把自己摘出去。

### 3.2 漏报：S4 只查一致性，漏了"集体忘升版本"（已补 S5）

- **漏洞**：如果四个页面**一起**忘了升 `?v=`，S4 会全绿；但浏览器拿的仍是旧缓存，Day 23 的错误文案改造等于没上线。
- **补法**：S5 用 `git log -1 --date=format:%Y%m%d -- <文件>` 取每个资源最后一次提交日期，要求 `?v=` 不早于它。
- **补上后第 2 轮立刻见红**：`api.js` / `main.js` / `detail.js` / `calc.js`（v=20261008，最后改动 20261015）、`check.js`（v=20261008，最后改动 20261011）。
- **这是真问题**：说明 Day 23 改完 `api.js` 后没有升版本号，老用户可能继续跑旧代码。
- **修法**：把这 5 个引用在四个页面里统一升到发布日 `v=20261019`，第 3 轮 S4/S5 同时通过。

### 3.3 检查器自己的另外三个坑（调试期发现，已修）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | 按关键词匹配文件名 | `check-secrets.sh` 因文件名含 `secret`，被 S2 判成"敏感文件被提交" | 改按**文件名形态**匹配（`.env` / `.pem` / `.key` / `credentials.json`） |
| 2 | 把注释当用户文案 | S10 把 `MESSAGES` 里的注释"不说 Failed to fetch"当成"漏给用户的技术术语" | 只取真正的**值行**（`KEY: '...'`） |
| 3 | 取错 HTTP 状态行 | 走代理时响应头有两行 `HTTP/`，`grep -m1` 取到代理的 `200 Connection Established`，把 405 报成 200 | 取**最后一行** |
| 4 | `grep -v` 的返回码 | 所有行都被白名单豁免时 `grep -v` 返回 1，被 `\|\| cat` 兜底误触发，白名单等于失效 | 区分返回码 1（全豁免，正常）与 ≥2（真出错） |

> 结论：**检查器本身也要被检查**。每一项都要求"故意弄坏能查出来"，只见过绿的检查项等于没写。
