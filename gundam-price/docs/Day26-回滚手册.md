# 回滚手册 ｜ 高达行情 v1.0

> 用法：出问题时**只看第一节和第二节**，别从头读。练的时候照第四节做，并把耗时填进 `Day26-回滚演练记录.md`。
> 一句话原则：**能退就先退，退完再查原因。** 回滚不是承认失败，是把用户从坏页面里救出来。

---

## 一、什么情况必须回滚（判断表）

先看现象，再对表。**「必须回滚」= 影响正在使用的人，且 30 分钟内改不好。**

| # | 现象 | 先花 30 秒确认什么 | 判定 | 动作 |
|---|---|---|---|---|
| 1 | 首页打不开（`404` / `5xx` / 白屏无内容） | 换无痕窗口 + 手机流量各试一次 | **必须回滚（P0）** | 直接退到上一版，退完再查上传/路由 |
| 2 | 页面框架在、卡片区域一片空白 | 打开 `/api/kits` 看是否 200；浏览器控制台有无红色报错 | **必须回滚（P0）** | 先退前端；若接口本身挂了，见第 8 条 |
| 3 | 价格、五算、档位算错（数字不对但页面正常） | 拿一台机体手算一遍五算 | **回滚（P1）** | 业务算错比页面打不开更伤信任，回滚最快 |
| 4 | 页脚版本号与刚发的不一致 | 打开 `<站点>/version.json` 看 version | **不回滚** | 是没覆盖成功 → 重传，别动代码 |
| 5 | 只有某个旧手机/某浏览器错乱 | 换一台设备复现 | **看影响面（P2）** | 记机型 + 截图，进下一版修；影响面大再回滚 |
| 6 | 文案错别字、链接写错但功能正常 | — | **不回滚** | 攒着下次一起修（热修一次也要走完整发布流程） |
| 7 | 写接口报错、打卡存不进去 | 看接口返回是 401 还是 500 | **不回滚前端** | 401 = 密钥/配置问题；500 = 云函数问题，见第三节 |
| 8 | 三条读接口全挂（`/api/kits` 500 或超时） | 云函数控制台看日志与最新部署时间 | **先修后端，不回滚前端** | 前端回滚也救不了没数据的后端；按第三节退云函数 |
| 9 | 数据库数据被写坏（价格被批量改错） | `SELECT` 抽样看几行 | **回滚前端无效** | 走数据恢复（第五节），前端不用动 |
| 10 | 密钥疑似泄漏 | 看密钥是否出现在代码/仓库/公网文件里 | **不是回滚能解决的（P0 安全）** | 立刻在控制台轮换密钥 → 再排查来源；回滚只会在旧代码里继续用同一把钥匙 |

### 回滚 or 热修？一张对照

| 情况 | 选回滚 | 选热修 |
|---|---|---|
| 修好要多久 | > 30 分钟 | < 10 分钟，且改动只有一两行 |
| 改哪里 | 多处文件 / 不确定根因 | 一个明确的位置 |
| 风险 | 边查边改容易越改越乱 | 改完能立刻用同一套流程验证 |
| 时间点 | 用户正在用（白天、有人反馈） | 深夜、几乎没人访问 |

> 拿不准就回滚。回滚是**已知的旧版本**，热修是**没验证过的新改动** —— 出事时前者更可信。

## 二、静态托管回退（3 分钟主路径）

### 前提（发布前就该备好）

| 前提 | 检查方式 |
|---|---|
| 上一版发布包在本地 | `gundam-price/releases/v0.9.0/index.html` 存在 |
| 上一版的版本号记得 | `cat gundam-price/releases/v0.9.0/version.json` → 0.9.0 |
| 站点地址能打开 | 根路径看到首页 |

包丢了也能救（从提交重建，约 10 秒）：

```bash
cd C:\Users\13546\Desktop\vibecoding打卡project
bash gundam-price/scripts/make-release.sh 0.9.0 efa8050
```

**强烈建议：提前在桌面放一份短路径副本**（如 `Desktop\rollback-v090`）。上传弹窗里粘贴含中文的长路径容易「找不到文件」（2026-10-23 演练实测卡了约 5 分钟），短路径 + 纯鼠标导航（左侧栏点桌面 → 双击进入）最稳。副本内容以 `releases/v0.9.0` 为准，每次改包后记得同步。

### 步骤（每步都有「怎么知道这步成了」）

| 步 | 做什么 | 怎么知道成了 | 计时点 |
|---|---|---|---|
| 1 | 判定要回滚，**先说一句「现在回滚」**（说给自己听，避免边查边改） | — | 开始计时 |
| 2 | 终端启动等待：`bash gundam-price/scripts/check-live.sh --wait-for 0.9.0` | 屏幕开始每 3 秒打印「线上仍是 v1.0.0」 | — |
| 3 | 控制台 <https://tcb.cloud.tencent.com/dev?envId=gundam-market-d7gnjqg3h1f2f156f#/static-hosting> → **文件管理**：先「上传文件」传 `releases/v0.9.0` 的 5 个根文件（`index.html`、`calc.html`、`detail.html`、`check.html`、`version.json`），再分别「上传文件夹」传 `js`、`css`、`img`、`data`，同名覆盖 | 根目录列表里 `version.json` 的更新时间变成刚才 | 上传开始 |
| 4 | 回终端看第 2 步那条命令 | 打印「检测到 v0.9.0 ✔」+ 切换耗时 | **脚本给出的秒数 = 回滚生效耗时** |
| 5 | 跑一次完整核验：`bash gundam-price/scripts/check-live.sh` | 首页 200、版本标记 0.9.0、接口 PASS | 验证开始 |
| 6 | 浏览器打开首页 + 点一张卡片 | 卡片正常、详情正常（页脚**没有**版本徽标 = 旧包，正常） | 记录总耗时 |

### 回退时必须知道的三个坑

| 坑 | 为什么会发生 | 怎么防 |
|---|---|---|
| **整包上传变成子目录** | 「上传文件夹」把文件夹名当一级路径，选中 `v0.9.0` 会落成 `/v0.9.0/index.html`，根路径还是坏页面 | 根文件走「上传文件」，子目录一个个「上传文件夹」；传完先看根目录有没有 `version.json` |
| **残留新文件** | 上传是「覆盖同名文件」，不是「清空后重传」。v1.0 新增的 `js/version.js` 会留在桶里 | 旧页面不引用它，无害；但要知道**线上桶里不是纯旧版**。要彻底干净就先清空再传（风险更大，不推荐在故障中做） |
| **子目录错位** | 传成了 `/v0.9.0/index.html`，根路径还是坏页面 | 步骤 5 的「首页 200」就是这道闸；不对就重传，别怀疑包 |
| **缓存假象** | 浏览器缓存了 v1.0 的 html/js | `Ctrl + Shift + R`；`check-live.sh` 带时间戳查询，不受缓存影响，以它为准 |

> 回滚**不动 Git**。代码没变，变的是公网上跑着哪个包。所以「回滚证据」不是提交记录，而是 `version.json` 的版本号变化。

## 三、云函数回退（备查，今天不实操）

> 为什么今天不练：云函数回退动的是后端，读接口一断，前端页面全空 —— 演练会污染真实数据。**先写清楚，真出事照做。**

### 触发条件

- 读接口 500 / 超时，且日志指向最近一次云函数部署；
- 新写的接口把老接口带崩（路由冲突、方法白名单写错）；
- 发布后 `N3`（未登记路径兜底）变成网关 `INVALID_PATH` —— 说明 `/api` 路由配置被动过。

### 步骤

| 步 | 做什么 | 怎么知道成了 |
|---|---|---|
| 1 | 控制台 → 云函数 <https://tcb.cloud.tencent.com/dev?envId=gundam-market-d7gnjqg3h1f2f156f#/scf> → 选中 `api` | 能看到函数详情与最近部署时间 |
| 2 | 先看**日志**：报错是 `ConfigError`（环境变量缺失）还是业务异常 | `ConfigError` → 不用回退代码，去补环境变量 |
| 3 | 若函数详情有「版本管理 / 发布版本」：选上一个可用版本 → 发布 | 部署时间更新，版本号变化 |
| 4 | 若没有该入口：用旧包重新部署 —— 上传 `cloudfunctions/api-deploy-day19.zip` 覆盖 | 部署成功，函数列表显示新时间 |
| 5 | 核验：`bash gundam-price/scripts/check-live.sh` | 健康接口 + 读接口 PASS |
| 6 | 补跑 `verify-project.sh` 的 N3 / N5 / N6 | 404 兜底、401 门锁、405 白名单都正常 |

### 两个必须记住的点

1. **环境变量不在 zip 里**。回退函数代码不会回退环境变量 —— 变量是环境级配置，改错了要单独改回来（4 个变量，见发布清单 5.3）。
2. **云函数侧目前没有「当前版本」的包**。仓库里只有 Day 18 / Day 19 的 zip，Day 22 / Day 24 的改动没有归档 zip —— **这是回滚链上的真实缺口**。补法很轻：每次改完云函数，`zip` 一份带日期的包放进 `cloudfunctions/`（已在 `.gitignore` 里忽略，属本地存档）。

## 四、回滚后验证（退完必须做，否则不知道是「退了」还是「坏了」）

| # | 验证项 | 命令 / 操作 | 通过标准 |
|---|---|---|---|
| 1 | 首页可访问 | `check-live.sh` | HTTP 200 且有内容（不是 197 字节的网关报错） |
| 2 | 版本是目标版本 | `check-live.sh` 的「版本标记」行 | `v0.9.0`（回退）或 `v1.0.0`（恢复） |
| 3 | 接口正常 | `check-live.sh` 的健康 / 读接口 | 200 + total=5 |
| 4 | 页面真能用 | 浏览器打开首页，点一张卡片 | 卡片渲染、详情能开、比价有数 |
| 5 | 计算器 | 顶部导航 → 五算计算器 → 输 5000 日元 | 出五算与档位 |
| 6 | 手机端 | 手机浏览器打开站点 | 能打开、不错乱 |

**六项全过才能说「回滚完成」**。只有 1、2 过，说明只是文件换了、业务没验 —— 那不算完成。

> **文件真伪的验收口径（2026-10-23 演练教训）**：新旧版本文件名相同，HTTP 200 验不出「传的是哪版」。严谨判定要**逐字节比对**：`wc -c < 本地文件` 与 `curl -s 线上地址 | wc -c` 相等才算数。至少要抽验 `index.html`、`js/main.js`、`data/data.json` 三个。

## 五、数据恢复（备查，今天不实操）

数据库没有一键回滚。按影响面从轻到重：

| 情况 | 做法 | 耗时量级 |
|---|---|---|
| 单条记录误删（`isDeleted = true`） | `UPDATE ... SET "isDeleted" = false WHERE id = '...'` | 1 分钟 |
| 某天价格录错 | 按 `data/data.json` 的 Git 历史找回当天值，`UPDATE` 覆盖 | 5 分钟 |
| 整表被批量改坏 | 用改动前导出的 SQL 回灌（发布清单 5.2 有导出命令） | 10 分钟 |
| 整库损坏 | 控制台按备份实例 / 时间点恢复（以后台实际入口为准）→ 再用 `db/schema.sql` 校验结构 | 30 分钟+ |
| 表结构改坏 | `db/schema.sql` 重建 + 回灌数据 | 30 分钟+ |

**顺序永远是**：先让页面能看（回滚前端）→ 再修数据。别在用户看到空白页的时候先去调数据库。

## 六、演练纪律

| 规矩 | 为什么 |
|---|---|
| 演练必须**恢复到最后版本**，不能停在旧版 | 停在旧版 = 线上跑着过期代码，比没演练更糟 |
| 每次演练**记时间**，不记「大概几分钟」 | 没有数字就没法回答「真出事敢不敢用」 |
| 演练选**没人访问的时段** | 演练期间公网确实在跑旧版 |
| 演练完**当场写记录** | 隔一天细节全忘，尤其是卡在哪一步 |
| 一次只练一条路径 | 静态 + 云函数 + 数据一起练，出错分不清是哪步的问题 |

### 本次演练建议目标

| 指标 | 目标 | 说明 |
|---|---|---|
| 回退生效（上传→版本号变化） | < 120 秒 | 决定「故障持续多久」的关键段 |
| 回退后验证（六项） | < 180 秒 | 决定「敢不敢宣布已恢复」 |
| 恢复到目标版本 | < 120 秒 | 与回退同一条路径 |
| 全程（含发呆、找入口） | < 10 分钟 | 第一次练一定会慢，重点是把卡点记下来 |

> 真出事那天，你的实际耗时 ≈ 演练时**最慢那一次**。所以要练到「不用想下一步做什么」为止。
